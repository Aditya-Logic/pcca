# Deployment

How to take this from a laptop to `pcca.mha.gov.in`. Three parts: running it locally, getting the domain, and putting it on a government server.

---

## Part 1 — Run it locally

### With Docker (recommended)

```bash
cd pcca-portal
cp .env.example .env

# Generate real secrets. The app refuses to start with placeholders.
cd backend && npm install && npm run keys:generate
# Paste the three lines it prints into .env, then:
cd ..

docker compose up -d
docker compose logs -f migrate     # watch the seed verify 85 / 196 / 253 / 912
```

Open `http://localhost:8080`.

### Without Docker

You need Node 20+ and PostgreSQL 15+ already running.

```bash
# 1. Database
createdb pcca_portal
createuser pcca_app --pwprompt

# 2. Backend
cd backend
npm install
cp ../.env.example .env
npm run keys:generate        # paste output into .env
# set PGHOST/PGUSER/PGPASSWORD to match what you just created
npm run db:migrate
npm run db:seed
npm start                    # API on :4000

# 3. Frontend, in a second terminal
cd frontend/public
python3 -m http.server 8080
```

Open `http://localhost:8080`. The page detects the API and switches from the embedded demo data to live records — you will see a "Connected to the API" toast.

If the API is not running, the page still works on the embedded dataset. That is deliberate, so the single HTML file can be opened standalone.

### Demo credentials

These exist **only** when `DEMO_MODE=true`. The app refuses to start with `DEMO_MODE=true` and `NODE_ENV=production` together, so they cannot reach a production server.

Super Administrator — full access to all 85 offices, moderation, audit, accounts:
```
superadmin@pcca.mha.gov.in
Demo@Pcca#2026
```

PAO Administrator for PAO(CRPF) — sees and uploads for that office only:
```
pao.crpf@pcca.mha.gov.in
Demo@Crpf#2026
```

PAO Administrator for PAO(CISF):
```
pao.cisf@pcca.mha.gov.in
Demo@Cisf#2026
```

**Sign-in is two steps.** The password gets you a challenge, not a session. The six-digit code is then:

- printed in the API log — `docker compose logs api | grep "one-time code"`
- and returned in the login response as `demoOtp`, so the browser can show it

Both only happen in demo mode. In production the code goes to the registered mobile via the SMS gateway and never appears in a log or a response.

Try proving the office scoping to yourself: sign in as `pao.crpf`, then request `/api/documents/office/pao-007`. You get a 403 — the office comes from the signed token, not from the URL.

### Before this goes anywhere real

```bash
# In .env
DEMO_MODE=false
NODE_ENV=production
```

Then delete the demo accounts:

```sql
DELETE FROM users WHERE email LIKE '%@pcca.mha.gov.in'
  AND full_name LIKE 'Demo %';
```

Create the real first super administrator directly in the database with a hash generated by `argon2`, or add a one-off bootstrap script. Never leave a known password on a live government system.

## Part 2 — Getting the domain

A `.gov.in` domain is not bought. It is allotted, free, to government bodies only, by the **National Informatics Centre (NIC)** under MeitY. The registry is the India Domain Registry at `registry.gov.in`.

### Who has to apply

Not you, and not a vendor. The application must come from the **Office of the Principal Chief Controller of Accounts, MHA** itself, submitted by a designated officer, usually of Under Secretary rank or above. NIC will not accept a request from a developer or a contractor.

### What the application needs

A request on official letterhead stating the proposed domain and its purpose. A nodal officer nominated in writing, with a government email address (`@gov.in` or `@nic.in`) and an official phone number — this person becomes the permanent point of contact. Approval from the competent authority in MHA. Details of where it will be hosted, which NIC will check against their hosting policy.

Because MHA already operates `mha.gov.in`, the cleanest route by far is a **subdomain** rather than a new second-level domain. `pcca.mha.gov.in` is a subdomain of an existing MHA domain, so it is approved by the MHA administrator who controls `mha.gov.in` — normally the MHA NIC cell — rather than requiring a fresh registry application. Ask the MHA NIC coordinator first. This can take days instead of the weeks a new registration takes.

### Timeline

A subdomain of an existing ministry domain: usually one to three weeks, mostly internal file movement. A new `.gov.in` registration: four to twelve weeks, longer if the justification is queried.

### The certificate

Government sites generally use certificates from the **Controller of Certifying Authorities (CCA)** ecosystem — in practice NICCA (NIC Certifying Authority) for NIC-hosted sites. Apply through the same NIC coordinator. A commercial or Let's Encrypt certificate works technically and is fine for a staging environment, but for a production `.gov.in` site expect to be told to use NICCA.

Start this in parallel with the domain request. The certificate is issued against the domain, so it cannot be applied for first, but the paperwork can be prepared.

## Part 3 — Government hosting

### Where it can live

**NIC National Data Centre** is the default and the path of least resistance for a `.gov.in` site. Facilities at Delhi, Hyderabad, Pune and Bhubaneswar. Apply through your MHA NIC coordinator with a resource request: CPU, RAM, storage, and expected traffic.

**MeghRaj / NIC Cloud** is the government cloud, suitable if you want to scale without a hardware request.

**An MHA-operated server**, if the ministry already runs its own infrastructure and prefers to keep this internal. Most likely if the portal ends up intranet-only.

### What to request

For this application, at this size, modest resources are plenty. Four vCPU, 8 GB RAM, and 100 GB of storage handles 85 offices and their documents comfortably. Ask for a separate staging instance — you will want somewhere to rehearse the deploy that is not production.

Storage is the one figure worth thinking about. 85 offices uploading a few files a month at up to 25 MB each, with every version retained forever, is roughly 25 to 60 GB a year. Ask for 250 GB if you can get it; growing a volume later is a change request.

### Mandatory compliance steps

These are not optional for a `.gov.in` site and each takes time, so start them early.

**GIGW compliance.** The Guidelines for Indian Government Websites are mandatory. They cover accessibility (WCAG 2.1 AA), bilingual content, mandatory pages, and content policy. The accessibility and bilingual work is already designed into this build — see `docs/design.md` and `docs/rules.md` — but the mandatory pages are not written yet. You need: Terms of Use, Privacy Policy, Copyright Policy, Hyperlinking Policy, Accessibility Statement, Help, Contact Us, and a Website Policies index. Draft these before the security audit, not after.

**Security audit.** A `.gov.in` site cannot go live without a clearance certificate from a **CERT-In empanelled auditor**. They will do a full application and infrastructure penetration test. Budget four to eight weeks including the retest after you fix what they find. Book the slot early — empanelled auditors have queues.

The build already anticipates most of what they look for: argon2id password hashing, httpOnly cookies rather than localStorage, parameterised queries throughout, CSP and HSTS, rate limiting on authentication, magic-byte validation on uploads, virus scanning, no secrets in frontend code, and an insert-only audit log. What they will flag is anything left at a default — so change every secret, turn off demo mode, and make sure `server_tokens off` is really in the live Nginx config.

**STQC certification** may be required depending on how MHA classifies the application. Ask your NIC coordinator whether it applies here.

**Data localisation.** All data stays on servers in India. NIC hosting satisfies this by definition. If anyone proposes a foreign cloud region, that is a compliance failure.

### Production deployment

```bash
# On the server
git clone <your-repo> /opt/pcca-portal
cd /opt/pcca-portal

cp .env.example .env
cd backend && npm run keys:generate     # paste into .env
cd ..

# .env must have:
#   NODE_ENV=production
#   DEMO_MODE=false
#   PUBLIC_ORIGIN=https://pcca.mha.gov.in
#   COOKIE_DOMAIN=.mha.gov.in
#   CLAMAV_HOST=clamav

# Certificates from NICCA
mkdir -p deploy/certs
cp /path/to/pcca.mha.gov.in.crt deploy/certs/
cp /path/to/pcca.mha.gov.in.key deploy/certs/
chmod 600 deploy/certs/*.key

docker compose up -d
docker compose run --rm migrate
```

Then enable 443 in `docker-compose.yml`, confirm the redirect from 80 works, and check the headers:

```bash
curl -sI https://pcca.mha.gov.in | grep -iE 'strict-transport|content-security|x-frame'
```

### Air-gapped or intranet-only

If the target has no internet access, build the images elsewhere and carry them in:

```bash
# On a connected machine
docker compose build
docker save pcca-portal-api pcca-portal-web postgres:15-alpine clamav/clamav:stable \
  -o pcca-images.tar

# On the target
docker load -i pcca-images.tar
docker compose up -d --no-build
```

Nothing in the frontend loads from a CDN and nothing in the backend calls an external service at runtime, so this works without modification. ClamAV signature updates will need a manual definition transfer.

### Backups

```bash
# Nightly, via cron
docker compose exec -T db pg_dump -U pcca_app pcca_portal | gzip > /backup/pcca-$(date +%F).sql.gz
tar czf /backup/uploads-$(date +%F).tar.gz -C /var/lib/docker/volumes/pcca-portal_uploads/_data .
```

Retain 30 days. **Rehearse a restore before you launch**, not after your first incident. A backup that has never been restored is not a backup.

## Checklist before go-live

Configuration — `DEMO_MODE=false`, `NODE_ENV=production`, every secret regenerated, demo accounts deleted, real super administrator created with a password only they know.

Infrastructure — TLS certificate installed and the 80-to-443 redirect confirmed, database not publishing a port, ClamAV running and `CLAMAV_HOST` set so scan status reads `CLEAN` rather than `SKIPPED`, backups running and a restore rehearsed.

Compliance — GIGW mandatory pages written, CERT-In audit passed and the certificate in hand, accessibility audit passed, Hindi content in place.

Data — the 85 derived station and organisation values reviewed by a human, contact details collected from each office, office statuses confirmed.

Operations — a runbook covering deploy, rollback, secret rotation and restore; the operating team has deployed it once themselves without help.

The four open blockers in `docs/memory.md` still need answers from the Pr.CCA office. Two of them — contact details and the derived-field review — have long turnarounds. Chase those now.
